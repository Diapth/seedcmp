## **一、产品定位与目标**

### **1\.1 产品定位**

AgentHub 后端是**多 Agent 协作平台的核心大脑**，负责：

- 统一接入市面上主流 Agent 平台（Claude Code、Codex、OpenCode 等），通过适配器层屏蔽 API 差异

- 以 IM 聊天为核心交互范式，支撑单聊、群聊、多 Agent 协作三种对话模式

- 提供主 Agent 协调器（Orchestrator），实现复杂任务的自动拆解、分派与结果聚合

- 管理产物全生命周期：生成 → 存储 → 预览 → 部署

### **1\.2 设计目标**

|目标|说明|
|---|---|
|**统一接入**|至少接入 2 个主流 Agent 平台，用户无感切换|
|**IM 原生**|消息即接口，聊天历史自动作为上下文|
|**智能协调**|群聊模式下自动识别是否需要 Orchestrator 介入|
|**产物闭环**|从代码生成到部署预览，聊天流内完成|
|**开放扩展**|支持用户自建 Agent，自定义 System Prompt \+ 工具集|

## **二、核心功能模块**

### **2\.1 IM 消息中心（Message Hub）**

#### **功能描述**

用户与 Agent、Agent 与 Agent 之间的所有消息流转枢纽。

#### **核心能力**

|能力|说明|优先级|
|---|---|---|
|消息收发|支持文本、图片、文件附件、语音占位、Markdown、Agent 卡片类消息；文本走 WuKongIM/TangSeng，Clowder 直聊可走 |P0|
|历史管理|按会话/线程组织消息，前端按 `conversationId` 分桶，后端按 `channelId + channelType` 同步频道消息|P0|
|上下文传递|Clowder 会话会缓存用户成功发送的文本消息，并作为 `promptContext` 传给后端桥接；Clowder thread 侧支持 manual context pins|P0|
|消息状态|前端统一为 `sending / success / failed / revoked / edited`；Agent 流式态为 `placeholder / chunk / final / cleanup`；产品态映射为 `queued -> streaming -> done / error / cancelled`|P0|
|实时推送|WuKongIM SDK 负责 WebSocket 连接、消息监听、会话同步和多端同步；后端 `AddMessagesListener` 监听消息并转发给 Clowder|P0|
|引用/回复|输入框维护 `replyTarget`，发送 payload 带 `replyRef`，气泡展示引用并支持跳转目标消息|P1|
|Pin 消息|后端支持置顶/取消置顶、置顶同步、清空置顶；群聊按群主/管理员或群配置校验权限|P1<br>|

#### 消息类型设计

#### 状态流转

用户消息发送：

```Plain Text
local append
  -> sending
  -> success       # 后端/WuKongIM 返回成功，消息与会话摘要合并
  -> failed        # 发送、上传、SDK 或权限失败
```

Agent 回复：

```Plain Text
queued / placeholder
  -> streaming / chunk
  -> done / final
  -> error / cancelled / cleanup
```

实现要求：

- 前端发送时先乐观插入本地消息，使用 `clientMsgNo` 做去重。

- 服务端返回的同一条消息必须通过 `messageId / clientMsgNo / streamKey` 合并，不新增重复气泡。

- Clowder streaming 的 `placeholder/chunk/final` 必须使用同一 `platformMessageId` 或稳定 `client_msg_no`。

- `cleanup` 事件不应生成空消息；后端已有 `ErrOutboundNoop` 保护。

- 失败消息保留在原位置，用户可通过气泡失败态重试。

#### 实时与历史同步

Message Hub 的同步分为三层：

1. WuKongIM WebSocket：浏览器通过 `wukongimjssdk` 获取连接地址，监听新消息、命令、会话变更与消息状态。

2. TangSeng REST 同步：前端通过 `/v1/message/channel/sync` 等接口按频道拉取历史消息，刷新或重连后恢复消息列表。

3. Clowder bridge：后端 `registerClowderBridgeListener()` / `MessagesListenWithRoles()` 将 IM 消息转成 Clowder inbound；Clowder outbound 通过 `/api/im-web/clowder/outbound` 写回 TangSeng。

会话 ID 约定：

- 单聊：`channelType = 1`，真实展示会话需要使用 TangSeng fake channel 规则处理双方 UID。

- 群聊：`channelType = 2`，`channelId` 为 group no。

- Clowder external chat：`externalChatId = "{channelType}:{channelIdOrFakeChannelId}"`。

- Clowder thread binding：`connectorId + externalChatId -> threadId`。

#### 上下文与 Pin

上下文分为短期上下文和长期上下文：

- 短期上下文：前端对 Clowder 会话缓存最近成功发送的用户文本消息，发送到 Clowder 直聊时作为 `promptContext`；默认适合保留最近若干轮用户意图。

- 长期上下文：后端代理 Clowder manual context pins，支持按 thread 管理长期上下文，并可标记源消息状态。

- IM 置顶：TangSeng `/v1/message/pinned` 是 IM 层 pin，影响聊天窗口和多端同步；Clowder manual context pin 是 Agent prompt 层 pin，二者应在 UI 上区分但可以互相引用源消息。

置顶权限：

- 单聊使用 fake channel 记录置顶。

- 群聊要求群存在且未删除；非群主/管理员时需要群配置允许成员置顶。

- 达到应用配置的频道置顶上限时拒绝新增置顶。

#### 引用、回复与 @

- 输入框 `replyTarget` 只对当前会话有效，切换会话时必须清理不匹配的引用目标。

- 发送 payload 中携带 `replyRef`，消息气泡展示引用摘要并支持跳转。

- @ 选择器从群成员/Agent 候选中插入 `@name`，归一化时保留 `mentions` 与 `mentionUids`。

- Clowder 群聊路由应优先识别明确 @、`directCatId`、`targetCatIds` 和 `/ask` 等命令，避免 Agent 无触发条件地插话。

验收流程：

1. 用户在 Clowder 直聊或群聊中输入请求并发送。

2. 前端立即插入本地消息，状态为 `sending`，生成 `clientMsgNo`。

3. 后端持久化成功后，前端将消息合并为 `success`，会话列表更新摘要。

4. 后端 Clowder listener 将消息归一为 `InboundMessage`，包含 sender、externalChatId、messageId、mentions 和 promptContext。

5. Clowder 根据 thread binding、Agent 目录、@/focus/权限路由给目标 Agent。

6. Agent 回复先以 ACK/reaction 或 placeholder 呈现，再以 chunk 持续更新同一条 Markdown 消息。

7. final 到达后，消息状态为 `success`，如有代码文件、部署请求或预览产物，则追加对应文件/卡片消息。

8. 用户刷新页面后，历史消息不重复；最终回复和附件可从 TangSeng 历史或 Clowder thread artifacts 恢复。

#### P0 验收标准

- 文本消息、图片、文件附件可以在单聊和群聊中发送、展示、失败重试。

- 历史消息按频道拉取，刷新/重连后没有重复消息。

- Clowder 直聊和群聊 @ Agent 能路由到正确 thread / Agent。

- Agent 流式回复在 UI 中合并为一条消息，final 后状态稳定。

- 发送消息时能携带必要上下文给 Agent，且不把密钥暴露到前端。

- WuKongIM WebSocket 与 REST 同步都可用，多端收到同一条消息。

- 错误、超时、权限拒绝、Clowder 不可用都有可见系统通知或失败态。

#### P1 验收标准

- 引用回复在发送、展示、跳转和切换会话时状态正确。

- Pin 消息支持单聊/群聊权限校验、同步和清空；Clowder manual context pin 可管理长期上下文。

- 支持 reaction/ACK，并能把 Clowder silent reaction 附着到目标用户消息。

- deployment、artifact、preview、diff、a2a\_handoff 等富媒体消息有稳定的 UI fallback。

- Agent 交接、部署状态、文件产物能在消息流中保留可追溯 metadata。

### **2\.2 主 Agent 协调器（Orchestrator）**

#### **功能描述**

群聊模式下的"项目经理"，自动理解用户意图、拆解任务、分派给合适的子 Agent、聚合产出并汇报。

#### **触发条件**

|场景|行为|
|---|---|
|无 @ 提及|Orchestrator 自动作为 Lead|
|显式 @coordinator|Orchestrator 作为 Lead|
|@ 多个 Agent|Orchestrator 作为 Lead|
|单 @ \+ 复杂任务关键词（协调/规划/部署等）|Orchestrator 作为 Lead|
|单 @ \+ 简单任务|直接路由到该 Agent|

#### **核心流程**

```Plain Text
用户输入
  → 意图识别 & 任务拆解
  → 生成协调计划（Coordination Plan）
  → 并行/串行分派子任务给各 Agent
  → 收集各 Agent 产出
  → 冲突检测 & 结果聚合
  → 在聊天流中汇报最终成果
```

#### **协调状态机**

```Plain Text
planning → dispatching → running → aggregating → succeeded
                    ↘ failed / cancelled
```

#### **子任务状态**

```Plain Text
todo → doing → done
  ↘ blocked → failed / cancelled
```

#### **用户故事**

\> **作为** 用户，**当我** 在群聊中说 "帮我做一个个人博客网站，前端用 React，后端用 Node\.js"，**我希望** Orchestrator 自动把这个任务拆成前端和后端两个子任务，分别分派给 Claude 和 Codex，**以便** 我不用手动协调两个 Agent 的工作。

### **2\.3 多 Agent 接入层（Agent Marketplace）**

#### **功能描述**

统一适配器层，屏蔽不同 Agent 平台的 API 差异，支持即插即用。

#### **接入平台**

|平台|clientId|协议|说明|
|---|---|---|---|
|Claude Code|`anthropic`|CLI \+ MCP|Anthropic 生态|
|Codex|`openai`|CLI \+ MCP|OpenAI 生态|
|Gemini|`google`|CLI \+ MCP|Google 生态|
|Kimi|`kimi`|CLI \+ MCP|Moonshot 生态|
|OpenCode|`opencode`|CLI \+ MCP|开源生态|
|A2A Agent|`a2a`|JSON\-RPC 2\.0|Google A2A 协议|

#### **Agent 配置模型（AgentProfile）**

每个 Agent 以 **AgentProfile** 为配置模型，采用 **Identity \+ Runtime Profile** 两层结构：

**Identity— 静态身份：**

- `id`, `name`, `displayName`, `nickname`

- `avatar`, `color`（前端展示）

- `mentionPatterns`（@提及别名，如 `@claude`、`@codex`）

- `roleDescription`（角色描述）

**Runtime Profile— 运行时能力：**

- `clientId`（底层提供商）

- `defaultModel`（默认模型）

- `cli`（CLI 配置：command, outputFormat, effort, contextWindow）

- `accountRef`（绑定的账户/API Key）

- `sessionStrategy`（会话策略：handoff / compress / hybrid）

- `mcpSupport`（是否支持 MCP 工具调用）

#### **用户自建 Agent**

用户可通过web界面创建自定义 Agent：

1. 设定名称、头像、@别名

2. 编写 System Prompt（角色设定）

3. 选择底层平台（Claude/Codex/\.\.\.）

4. 保存后即可在聊天中 @ 使用

#### **用户故事**

\> **作为** 用户，**当我** 想同时使用 Claude 和 Codex 处理同一个项目，**我希望** 在聊天列表中看到它们作为独立的"联系人"，**以便** 我可以像发消息一样分别或同时与它们对话。

### **2\.4 A2A Agent 间通信**

#### **功能描述**

Agent 之间可以通过 `@提及` 进行协作，形成工作链（Worklist）。

#### **A2A Handoff 机制**

```Plain Text
用户 @Claude: "写一个 React 组件"
  → Claude 生成代码
  → Claude 回复末尾: "@Codex 请帮我写这个组件的单元测试"
  → 系统自动检测到 @Codex
  → 触发 A2A Handoff，将任务转交给 Codex
  → Codex 收到带有上下文的提示，开始写测试
```

#### **防护机制**

|机制|说明|
|---|---|
|深度限制|A2A 链最大深度 15 层，防止无限递归|
|Ping\-pong 防护|同一对 Agent 来回超过 4 次自动阻断|
|Anti\-cascade|若 Agent 已是某个活跃 multi\-mention 的目标，拒绝新请求|
|超时保护|每条 A2A 消息 3\-20 分钟超时|

#### **用户故事**



\> **作为** 用户，**当我** 让 Claude 写代码后，Claude 主动说 "@Codex 请 review 这段代码"，**我希望** Codex 能自动收到这个请求并开始 review，**以便** 我不用手动复制粘贴代码到另一个对话。

### **2\.6 部署发布（Deployments）**

```Plain Text
用户/Agent 发起部署请求

  → 用户确认（或自动确认）
  → 生成部署任务
  → 执行部署（静态站点/源码包/容器计划）
  → 返回部署状态卡片（含预览链接/下载链接）
```

#### **部署类型**

|源码包下载|打包为 \.tar\.gz|P0|

### **2\.8 会话管理（Session Management）**

#### **功能描述**



管理 Agent 与底层 LLM 的会话生命周期，优化上下文窗口使用。

#### **会话策略**

|策略|说明|适用场景|
|---|---|---|
|`handoff`|上下文满时 seal 旧 session，开启新 session|长对话|
|`compress`|自动压缩历史消息|上下文敏感任务|
|`hybrid`|handoff \+ compress 结合|通用场景|

#### **Session Chain**



```Plain Text
Session 1 (active) → fillRatio 超过阈值 → seal → Session 2 (active)
                     ↓
              保留引用关系，支持上下文回溯
```

#### **Self\-heal 机制**

- 缺失 session → 自动重建

- Token 超限 → 清除 session 重试

- CLI 超时 → 清除 session 重试

- 瞬态错误 → 最多 2 次自动重试

|机制|说明|
|---|---|

```TypeScript
// AgentRouter.routeExecution() 核心逻辑
async function routeExecution(message, options) {
  // 1. 解析目标 Agent
  const { resolvedAgentIds, explicitMentionAgentIds } = parseAllMentions(message);

  // 2. 选择 Lead Agent（决定是否启用 Coordinator）
  const { leadAgentId, participantAgentIds, mode } = selectLeadAgent(
    resolvedAgentIds, explicitMentionAgentIds, message
  );

  // 3. 根据模式路由
  if (mode === 'coordinator') {
    // Coordinator 模式：Orchestrator 作为主 Agent
    return routeWithCoordinator(message, leadAgentId, participantAgentIds);
  } else if (intent === 'ideate' && resolvedAgentIds.length > 1) {
    // 并行模式：多 Agent 独立响应
    return routeParallel(message, resolvedAgentIds);
  } else {
    // 串行模式：单 Agent 或顺序执行，支持 A2A 扩展
    return routeSerial(message, resolvedAgentIds);
  }
}
```



#### **3\.1\.2 提及解析规则**



```TypeScript
// parseAllMentions 解析顺序
function parseAllMentions(message) {
  // 1. 解析群提及（group mention）
  //    @all, @thread, @全体{displayName}, @all-{agentGroupId}
  const groupMentions = parseGroupMentions(message);

  // 2. 解析个体提及
  //    Longest-match-first + token boundary
  //    避免 @opus-45 误命中 @opus
  const individualMentions = parseMentionsRaw(message);

  // 3. Position-aware union（去重并保留位置信息）
  return unionMentions(groupMentions, individualMentions);
}
```

3\. **最近健康回复者（\`last\-replier\`）** — 当前对话最后回复的 Agent

```TypeScript
  if (strategy.type === 'handoff') {
```

```TypeScript
function selectLeadAgent(resolvedAgents, explicitMentions, message): LeadSelection {
  // 无显式提及 → Coordinator
  if (explicitMentions.length === 0) {
    return { leadAgentId: 'coordinator', mode: 'coordinator', reason: 'no_mention' };
  }

  // 显式 @coordinator → Coordinator
  if (explicitMentions.includes('coordinator')) {
    return { leadAgentId: 'coordinator', mode: 'coordinator', reason: 'explicit_coordinator' };
  }

  // 多提及 → Coordinator
  if (explicitMentions.length > 1) {
    return { leadAgentId: 'coordinator', mode: 'coordinator', reason: 'multi_mention' };

  // 单提及 + 复杂任务关键词
  const complexKeywords = ['协调', '分工', '规划', 'deploy', 'plan', 'architect'];
  if (complexKeywords.some(kw => message.includes(kw))) {
    return { leadAgentId: 'coordinator', mode: 'coordinator', reason: 'complex_task' };
  }

  // 简单任务 → 直接路由
  return { leadAgentId: explicitMentions[0], mode: 'direct', reason: 'simple_task' };
}
```

### **3\.4 A2A Agent 间通信**



#### **3\.4\.1 A2A Handoff 检测**



```TypeScript
// A2A Mention 检测规则
function parseA2AMentions(content: string, fromAgentId: string): AgentId[] {
  // 1. 剥离围栏代码块（避免代码中的 @ 被误匹配）
  const textWithoutFences = stripCodeFences(content);

  // 2. 仅匹配行首 mention（可带前导空白/markdown 前缀）
  const lines = textWithoutFences.split('\n');
  const mentions: AgentId[] = [];

  for (const line of lines) {
    const match = line.match(/^\s*(?:>\s*)*@(\w+)/);
    if (match) {
      const agentId = resolveMention(match[1]);
      if (agentId && agentId !== fromAgentId) {
        mentions.push(agentId);
      }
    }
  }

  // 3. Longest-match-first + token boundary
  // 4. 上限 MAX_A2A_MENTION_TARGETS = 2
  return mentions.slice(0, MAX_A2A_MENTION_TARGETS);
}
```

```TypeScript
function updateStreakOnPush(entry: WorklistEntry, from: AgentId, to: AgentId): void {
  const pair = getOrderedPair(from, to);
```

```TypeScript
async function postMessage(request) {

    threadId,
    content,
    sender: invocation.agentId,
    deliveryStatus: 'queued',
    mentions
  });

  // 6. A2A 调度
  if (mentions.length > 0) {
    await enqueueA2ATargets(threadId, mentions, content);
  }

  // 7. WebSocket 广播
  socketManager.broadcastAgentMessage(threadId, message);
```
