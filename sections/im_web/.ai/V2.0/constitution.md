# TangSengDaoDaoWeb Vue Constitution

## Core Principles

### I. Monorepo Modular Isolation

TangSengDaoDaoWeb work MUST preserve the package boundaries established by the
Vue monorepo. Base UI and shared services belong in the base package; login,
contacts, data synchronization, and chat application code MUST remain in their
own packages or app areas. Feature work MUST NOT introduce circular package
dependencies, shared-state shortcuts, or cross-package imports that bypass the
existing ownership model. Page components consume state and render UI; data
acquisition, SDK synchronization, and durable state transitions belong in the
data-source stores.

Rationale: the client is already split by product capability. Keeping that
shape makes V2.0 work independently testable, reviewable, and less likely to
regress unrelated chat flows.

### II. Minimalist Interface System

All user-facing UI MUST follow the project's restrained minimalist design
system. Light mode uses white and pale neutral surfaces; dark mode uses clean
charcoal surfaces; panels, inputs, and message cells rely on 1px separation,
clear spacing, high-contrast text, and short transitions. Components MUST use
scoped styles or equivalent local style isolation and MUST NOT introduce
utility-first global styling systems. Personal and group avatar fallbacks MUST
be generated by the client avatar component or an equivalent branded fallback,
not generic broken-image or placeholder assets.

Rationale: IM screens are dense and repeated all day. A quiet, consistent UI
reduces cognitive load and prevents V2.0 feature expansion from becoming visual
clutter.

### III. SDK and Store Single Source of Truth

Realtime SDK listeners, command handling, message synchronization, connection
state, and channel metadata MUST be registered and reconciled through the
data-source store layer. Vue components MUST NOT mount duplicate global SDK
listeners or mutate durable message and conversation state outside the stores.
Command messages such as revokes, unread clears, group updates, and online
changes MUST be normalized into store state before UI presentation.

Rationale: realtime systems fail quietly when multiple UI instances subscribe
or patch state independently. A single reactive source keeps recovery,
refreshes, and multi-device updates coherent.

### IV. Backend-Aligned Capability Completion

V2.0 work MUST close user-facing gaps against the available TangSengDaoDaoServer
and WuKongIM capabilities before inventing new product surfaces. Messaging,
media, message actions, reactions, receipts, pinned messages, reminders, group
management, QR flows, account settings, notifications, search, workplace,
robot, report, and realtime recovery features MUST be planned from verified
backend behavior and exposed only when the user can complete the flow safely.
Administration-only backend features MUST stay out of the end-user chat client
unless they directly support chat, group, account, workplace, robot, report, or
notification workflows.

Rationale: the primary V2.0 risk is partial integration. Users need complete
flows with honest unavailable states, not scattered buttons backed by uncertain
behavior.

### V. Build, Test, and Review Gates

Every implementation slice MUST include the full quality loop: build the
affected code, run the relevant automated tests, run the user-flow or smoke
checks defined by the plan, and complete code review before the slice is called
done. Build failures, type errors, lint failures, failing tests, skipped
required smoke checks, and unresolved review findings block completion. If any
required verification cannot run, the reason, risk, and replacement evidence
MUST be recorded in the plan or task notes before review.

Rationale: V2.0 spans realtime messaging, group permissions, security actions,
and media workflows. The only reliable finishing line is evidence: built code,
tested behavior, and reviewed changes.

## Engineering Constraints

- Work MUST respect the existing package layout under `sections/im_web`.
- V2.0 specification, planning, and task artifacts MUST live under
  `sections/im_web/.ai/V2.0` unless a later governance decision changes the
  feature directory.
- UI changes MUST preserve responsive behavior, text containment, and stable
  dimensions for repeated controls such as conversation rows, message cells,
  member rows, drawers, modals, and toolbars.
- Network recovery, session kickout, destructive actions, and security-related
  flows MUST have explicit user-visible states.
- Backend-dependent features MUST include unavailable or disabled states when
  the required service response is missing, unsupported, or permission-denied.
- Destructive actions such as mutual deletion, group disbanding, ownership
  transfer, account deletion, device removal, and security setting changes MUST
  require explicit confirmation.
- Performance-sensitive message and conversation work MUST define measurable
  acceptance evidence before implementation starts.

## Development Workflow

1. **Specify**: Describe user value, independent scenarios, edge cases, and
   measurable success criteria without implementation details.
2. **Plan**: Identify affected packages, backend capabilities, data ownership,
   UI states, permission boundaries, and the exact build, test, smoke, and code
   review evidence required for completion.
3. **Task**: Generate tasks by independently testable user story. Each story
   MUST include implementation tasks, build tasks, automated test tasks,
   user-flow or smoke verification tasks, and a code review task.
4. **Build Code**: Implement narrowly within the planned package boundaries.
   The affected workspace MUST build before any story is marked complete.
5. **Test Completely**: Run unit, integration, store, UI, realtime recovery,
   and smoke tests appropriate to the story. Tests that are not applicable MUST
   be explicitly marked as not applicable with a reason.
6. **Code Review**: Reviewers MUST check constitution compliance, user-facing
   behavior, backend alignment, state ownership, permission handling, recovery
   paths, UI consistency, and test/build evidence before approval.
7. **Close**: A story is complete only when build evidence, test evidence,
   smoke evidence, and review outcome are recorded and no blocking issue
   remains.

## Governance

This constitution supersedes conflicting local practices for TangSengDaoDaoWeb
V2.0 work. Amendments require a written rationale, a version bump following
semantic versioning, and synchronization of dependent Spec Kit templates.

Versioning policy:

- MAJOR: removes or redefines a core principle, changes required quality gates,
  or changes artifact governance in a way that affects existing plans.
- MINOR: adds a principle, adds required workflow evidence, or materially
  expands constraints.
- PATCH: clarifies wording, fixes errors, or updates examples without changing
  obligations.

Compliance review is mandatory at plan creation, after design, during task
generation, before story completion, and during code review. Any exception MUST
be documented with scope, rationale, risk, and follow-up owner. Unresolved
exceptions block release readiness.

## Appendix A: Testing Specification

### A.1 测试分层模型

V2.0 测试按以下五层从上到下递增投入，每层测试必须在本层验证通过后方可进入下一层：

```
┌─────────────────────────────────────────────────────┐
│  Layer 5 · E2E / Smoke (Story Close 前手动/自动跑)   │
├─────────────────────────────────────────────────────┤
│  Layer 4 · Integration (多 Store / SDK 联动)         │
├─────────────────────────────────────────────────────┤
│  Layer 3 · Store / Unit (单 Store 状态机、工具函数)   │
├─────────────────────────────────────────────────────┤
│  Layer 2 · Component (Vue 组件渲染、交互)            │
├─────────────────────────────────────────────────────┤
│  Layer 1 · Build Gate (lint + type-check + unit)    │
└─────────────────────────────────────────────────────┘
```

每层 **N/A** 必须显式标注原因，否则视为未完成。

### A.2 Layer 1 — Build Gate（每次提交必跑）

| 检查项 | 命令 | 通过标准 |
|---|---|---|
| TypeScript 类型 | `pnpm -r exec vue-tsc --noEmit` | exit 0 |
| Lint | `pnpm lint` | 无 error |
| 单元测试（工具函数/纯函数） | `pnpm test:unit` | 全部 green |
| Workspace 构建 | `pnpm build` | exit 0 |

```
# 每次 PR / Story close 前必须全部通过
pnpm type-check && pnpm lint && pnpm test:unit && pnpm build
```

### A.3 Layer 2 — Component Tests（交互组件必须写）

- **目标**：所有用户可交互组件（发送消息、弹窗确认、列表操作、抽屉切换）
- **工具**：Vitest + @testing-library/vue
- **覆盖场景**：
  - 默认渲染（happy path）
  - 加载态（loading skeleton）
  - 空状态（empty state）
  - 错误态（error state）
  - destructive action 确认弹窗触发/取消
  - optimistic update（发送中 → 成功/失败）
- **不写**：纯展示组件、样式组件，仅由 props 驱动无交互的组件可选跳过

### A.4 Layer 3 — Store / Unit Tests（数据层变更必须写）

- **目标**：所有 data-source store、SDK 消息归一化、工具函数
- **工具**：Vitest + fake SDK mock
- **覆盖场景**：
  - SDK 消息 → Store 状态归一化正确性
  - 连接状态切换（connected / reconnecting / failed）时 Store 行为
  - 权限边界（有权限 vs 无权限的 UI 状态差异）
  - 多设备消息去重逻辑
  - offline queue 处理（消息在离线状态下的暂存与重发）
  - destructive action 状态机（发送中 → pending → confirmed / failed）
- **覆盖率目标**：Store 和工具函数覆盖率 ≥ 70%

### A.5 Layer 4 — Integration Tests（多模块联动必须写）

- **目标**：跨 Store 协作、Store ↔ SDK 联动
- **工具**：Vitest（可引入真实 store 实例 + fake SDK）
- **覆盖场景**：
  - 会话列表更新 + 消息列表更新同时触发
  - 断线重连后多 Store 同步恢复
  - 群组成员变更 → 消息发送权限变更联动

### A.6 Layer 5 — E2E / Smoke Tests（Story Close 前必须跑）

- **工具**：Playwright（自动化 E2E）
- **覆盖场景**（核心用户流，必须全部绿灯）：
  - UC-1：用户登录 → 发送文本消息 → 收到回复
  - UC-2：创建群聊 → 邀请成员 → 群内发送消息
  - UC-3：发送图片/文件 → 媒体预览 → 下载
  - UC-4：断网 30s → 重连 → 消息完整性验证
  - UC-5：destructive action（删除聊天、退出群聊）确认弹窗 → 确认 → 状态正确
  - UC-6：多设备同时在线 → 消息去重 → 各端展示一致
- **手动 Smoke Check**（自动化 E2E 覆盖前，PR author 必须本地验证）：
  - UI 渲染正确（无布局错位、无 console error）
  - realtime 连接状态 indicator 正确显示
  - 断线重连后消息不丢失

### A.7 Realtime 专项测试（手动验证，记录结果）

以下场景难以自动化覆盖，需要手动测试并记录结果到 issue：

| 场景 | 验证方式 | 通过标准 |
|---|---|---|
| 断网 30s 后重连 | 手动断网测试 | 消息完整恢复，无丢失 |
| 大量消息（1000+）滚动 | 手动压力测试 | 滚动流畅，无 JS exception |
| 多设备同时在线 | 多浏览器实例 | 消息去重正确，各端展示一致 |
| 弱网 optimistic update | Network 节流测试 | 发送失败时正确回滚 UI |

### A.8 性能基准（Performance Budget）

| 指标 | 目标 | 测量方式 |
|---|---|---|
| 首屏加载 | FCP < 2s（Lighthouse） | 手动跑 Lighthouse |
| 消息列表滚动（100条） | FPS ≥ 50 | Chrome DevTools Performance |
| Store 状态更新延迟 | < 50ms（单次状态变更） | Vitest benchmark |
| 消息发送 optimistic UI | < 100ms 反馈 | 人工掐表 |

性能退化（同比下降 > 20%）需要记录到 issue 并经 review 通过后方可合并。

### A.9 观测与调试规范

- **连接状态**：连接/重连/断开必须在 UI 有明确 indicator
- **SDK 异常**：SDK 抛出的未捕获异常必须打印到 console，包含 `timestamp`、`event`、`payload`
- **日志格式**：`[WS] connected`、`[WS] reconnecting (attempt 3)`、`[SDK] message normalized: {type}`
- **断点调试**：建议在 `store/sdk.ts` 的消息处理入口打日志，便于追踪消息流向

### A.10 离线 / 弱网处理规范

- **Offline Queue**：消息在离线状态下暂存到 localStorage/IndexedDB，重连后自动重发
- **Optimistic Update**：发送时立即渲染消息（status: sending），收到 ACK 后更新为 sent，失败后回滚并显示错误
- **Weak Network**：网络超时时重试 2 次，每次间隔 2s，2 次均失败后标记为 failed 并提示用户

### A.11 可访问性（A11y）最低要求

- 所有可交互元素必须有键盘焦点（Tab / Escape / Enter 行为正常）
- 图标类按钮必须有 `aria-label`
- 颜色对比度符合 WCAG AA（文字 4.5:1，大字 3:1）
- 表单错误提示必须关联对应字段（`aria-describedby`）
