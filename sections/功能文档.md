# （前端）具体功能分析文档

本文档对比 `sections/im_web` 与 `TangSengDaoDao/TangSengDaoDaoWeb` 两套前端在同一套 `sections/im` 后端能力之上的实现方式。两者都不直接实现 IM 后端业务逻辑，前端主要负责登录态维护、REST API 调用、WuKongIM WebSocket SDK 接入、消息/会话/联系人/群组状态管理和 UI 呈现。

对比对象：

- `sections/im_web`：本仓库内 Vue 3 + Vite + Pinia + Arco Design Vue 实现，核心目录为 `sections/im_web/apps/chat`、`sections/im_web/packages/datasource-vue`、`sections/im_web/packages/base-vue`、`sections/im_web/packages/contacts-vue`、`sections/im_web/packages/login-vue`。
- `TangSengDaoDaoWeb`：GitHub 仓库 [TangSengDaoDao/TangSengDaoDaoWeb](https://github.com/TangSengDaoDao/TangSengDaoDaoWeb)，本次对比参考提交 `c95247a`，主要是 React 17 + react-app-rewired/Webpack + Electron/Tauri + 自研 `WKApp` 模块体系，核心目录为 `apps/web`、`packages/tsdaodaobase`、`packages/tsdaodaodatasource`、`packages/tsdaodaocontacts`、`packages/tsdaodaologin`。

整体差异概览：

| 维度 | `sections/im_web` | `TangSengDaoDaoWeb` |
| --- | --- | --- |
| 前端框架 | Vue 3 Composition API + Pinia | React class component + Provider/VM 模式 |
| 构建方式 | Vite 5 + pnpm workspace | react-app-rewired/Webpack + Yarn/Turbo workspace，兼容 Electron/Tauri |
| 状态中心 | Pinia store 明确拥有用户、SDK、会话、消息、联系人、群组状态 | `WKApp` 全局单例 + SDK manager + 页面 VM 共同维护状态 |
| SDK 接入 | `useSdkStore` 初始化 SDK，注册 CMD/Message listener，业务状态落入 Pinia | `WKApp.startup` 初始化 SDK，`DataSourceModule` 注册 SDK provider callback，业务状态多保留为 SDK 对象 |
| 同步策略 | REST 增量同步 + WebSocket 实时事件 + 重连恢复 + 本地去重/补偿 | 以 SDK `conversationManager`、`chatManager`、`channelManager` 为主，provider callback 负责后端数据转换 |
| UI 组织 | 路由页面、store、组件边界较清晰 | 模块注册、端点扩展、route stack、VM 组合能力更强 |
| 新增能力 | 在原 IM 能力上增加 Clowder/AI 联系人、猫猫成员、流式合并、项目群等扩展 | 原生 IM PC/Web 客户端能力完整，包含桌面壳、菜单、通知、组织架构等 |

两者共同前端链路可以概括为：

1. 登录接口返回 `uid`、`token` 和用户资料，前端持久化登录态。
2. 前端调用 `users/{uid}/im` 获取 WuKongIM 连接地址。
3. 通过 `wukongimjssdk` 设置 `uid/token` 并建立 WebSocket 连接。
4. 首屏或切换会话时通过 REST 接口同步最近会话、频道资料、消息列表、联系人、群成员等。
5. WebSocket 收到普通消息或 CMD 消息后，前端更新本地状态并刷新 UI。
6. 断线、刷新、重连后再次通过 REST 增量同步补齐状态，避免只依赖实时事件。

## 消息同步机制

### 共同依赖的前端输入

两套前端都依赖相同类型的后端和 SDK 数据入口：

- WebSocket 实时消息：`wukongimjssdk` 的 `chatManager.addMessageListener`、`addMessageStatusListener`、`addCMDListener`。
- 历史消息同步：`POST message/channel/sync`，参数包含 `channel_id`、`channel_type`、`limit`、`start_message_seq`、`end_message_seq`、`pull_mode`。
- 消息扩展能力：撤回、编辑、已读回执、表态、置顶、提醒等接口由前端调用，但状态事实仍来自后端或 SDK 回调。

### `sections/im_web` 的实现

`im_web` 把消息状态集中在 `packages/datasource-vue/src/stores/messageStore.ts`，SDK 连接与监听注册集中在 `stores/sdk.ts` 与 `cmd/index.ts`。

核心流程：

1. `useUserStore.applyLoginResult` 保存 token 后调用 `useSdkStore.initializeSDK(uid, token)`。
2. `useSdkStore.initializeSDK` 设置 `WKSDK.shared().config.uid/token`，并通过 `users/{uid}/im` 解析 WebSocket 地址。
3. 首次初始化时只注册一次 `registerCMDListeners()`、`registerMessageListeners()` 和自定义消息类型。
4. SDK 连接成功后执行 `runRecoverySync()`，由 `conversationStore.recoverAfterReconnect()` 同步会话、消息、置顶、提醒，再由 `messageStore.retryPendingQueue()` 处理发送失败或未确认的本地队列。
5. 打开会话时，`ChatView.vue` 调用 `messageStore.syncMessages(channelId, channelType, { hydrateVisibleHistory: true })`，并安排 2.5 秒、10 秒、30 秒的可见历史刷新，补齐后端异步落库或 AI 回复延迟。

消息列表的本地结构是普通对象数组，按 `channelId-channelType` 存在 `messages` 字典中。`messageStore.syncMessages` 会：

- 读取当前频道已知最大 `messageSeq`。
- 如果需要首屏可见历史，会根据最近会话的 `last_msg_seq` 拉取靠近最新消息的窗口。
- 调用 `message/channel/sync` 后进入 `mergeSyncedMessages`，将后端消息标准化为前端 `Message`。
- 通过 `clientMsgNo`、`messageID` 进行去重，避免本地 pending、SDK 回推、历史同步三条路径生成重复气泡。
- 对可见窗口执行补拉，默认窗口上限为 `VISIBLE_HISTORY_WINDOW_LIMIT`。
- 排序后更新当前频道消息，并同步最近会话摘要。

实时消息处理在 `registerMessageListeners` 中完成：

- 收到非持久化消息直接忽略。
- 使用 `resolveVisibleMessageChannel` 修正单聊中“channelID 等于自己、fromUID 是对方”的可见频道归属，确保好友单聊落到对方 UID 的会话里。
- 自己发出的消息在全局监听中跳过，因为发送函数已经先写入本地 pending 消息；否则 SDK 回推和本地 optimistic entry 会重复。
- 对方消息调用 `messageStore.addRealtimeMessage`，并在当前正在查看该频道时清未读。

发送路径也由 `messageStore` 持有：

- `sendMessage` 先创建本地 pending 文本消息，写入队列并立即展示。
- 调用 `WKSDK.shared().chatManager.send` 后，用 SDK 返回的 `clientSeq` 建立 ack 别名。
- `addMessageStatusListener` 收到 ack 后，根据 `clientSeq -> clientMsgNo` 更新 pending 消息的 `messageID`、`messageSeq`、发送状态。
- 文本、图片/文件、语音都有 retry payload；发送失败后标记 `retryable`，重连时 `retryPendingQueue` 会把仍处于 sending 的消息转为可重试。
- 媒体消息先通过 `file/upload` 获取上传地址并上传文件，再构造 SDK 的图片、文件或语音内容发送。

CMD 消息处理也落在 store：

- `typing` 更新 `typingState`，三秒后自动消失。
- `messageRevoke` 标记本地消息撤回。
- `channelUpdate`、`groupAvatarUpdate` 会清理频道/群缓存并重新拉取。
- `unreadClear`、`conversationDeleted` 更新最近会话状态。
- `friendRequest`、`friendAccept`、`friendDeleted`、群成员变更类 CMD 会通过 store 或浏览器事件触发联系人/群组重拉。

因此，`im_web` 的消息同步特点是：前端自己做状态规范化、去重、补拉、重连恢复和发送补偿，SDK 主要作为收发通道和连接状态来源。

### `TangSengDaoDaoWeb` 的实现

TangSengDaoDaoWeb 的消息同步更贴近 WuKongIM SDK 原生模型。核心文件是：

- `packages/tsdaodaodatasource/src/module.ts`
- `packages/tsdaodaodatasource/src/conversation.ts`
- `packages/tsdaodaobase/src/Pages/Chat/vm.ts`
- `packages/tsdaodaobase/src/Components/Conversation/vm.ts`
- `packages/tsdaodaobase/src/module.tsx`

`DataSourceModule` 在初始化时把后端能力注册到 SDK provider：

- `syncConversationsCallback` 调 `conversation/sync`，再用 `Convert.toConversation` 转成 SDK `Conversation`。
- `syncConversationExtrasCallback` 调 `conversation/extra/sync`。
- `syncMessageExtraCallback` 调 `message/extra/sync`。
- `syncRemindersCallback` 调 `message/reminder/sync`。
- `messageReadedCallback` 调 `message/readed`。
- `channelInfoCallback` 调 `channels/{channelID}/{channelType}` 并转成 SDK `ChannelInfo`。
- `syncSubscribersCallback` 调 `groups/{groupNo}/membersync` 并转成 SDK `Subscriber`。

历史消息由 `ConversationProvider.syncMessages` 负责：

- 调 `message/channel/sync`。
- 使用 `Convert.toMessage` 把后端结构转成 SDK `Message`。
- 返回给 `ConversationVM` 继续排序、插入时间分割、更新页面。

会话页 `ConversationVM` 直接监听 SDK：

- `chatManager.addMessageListener` 收到当前频道消息后封装为 `MessageWrap` 并追加。
- `chatManager.addMessageStatusListener` 根据 ack 更新发送状态。
- `chatManager.addCMDListener` 处理撤回和消息扩展同步。
- `conversationManager.addConversationListener` 同步当前打开会话的 unread、lastMessage 等。

打开会话时，`ConversationVM.requestMessagesOfFirstPage` 会根据当前会话的 `remoteExtra.keepMessageSeq`、`browseToMessageSeq`、未读数和最近消息序号决定初始拉取位置。上拉、下拉分别由 `pullupMessages` 和 `pulldownMessages` 调 `conversationProvider.syncMessages` 实现。

发送路径同样保留 SDK 对象：

- `ConversationVM.sendMessage` 调 `WKSDK.shared().chatManager.send(content, channel, setting)`。
- 返回的 SDK `Message` 包装成 `MessageWrap` 后放入静态 `sendQueue`。
- UI 再将后端同步消息与 `sendQueue` 合并显示。

全局 `BaseModule` 也注册了普通消息监听，用于通知、声音、频道资料刷新和成员同步，但当前会话的消息展示主要由 `ConversationVM` 负责。

### 对比结论

| 对比点 | `sections/im_web` | `TangSengDaoDaoWeb` |
| --- | --- | --- |
| 消息状态形态 | 自定义普通对象，Pinia 持有 | SDK `Message`/`Conversation`/`ChannelInfo` 对象为主 |
| 历史同步 | store 主动调用 REST，自己合并去重 | SDK provider + `ConversationProvider` 转换后交给 VM |
| 实时消息 | 全局 listener 归一化后写 store | 当前会话 VM 和全局 BaseModule 分别监听 |
| 自己发出的消息 | 本地 pending 优先，SDK 回推跳过，ack 更新 pending | SDK send 返回消息进入 sendQueue，再与历史消息合并 |
| 重连恢复 | 显式 `recoverAfterReconnect` + pending retry | SDK 重连后重新 sync 会话，页面 VM 依赖 SDK manager 状态 |
| 去重与补偿 | 前端显式处理 clientMsgNo/messageID/AI 流式合并 | 更多依赖 SDK 和 `MessageWrap` 排序、sendQueue |

`im_web` 更适合需要强控制历史补拉、AI/Clowder 消息合并、多端重复保护的场景；TangSengDaoDaoWeb 更适合保持原版 WuKongIM SDK 的对象模型和 PC 客户端扩展体系。

## 好友对话更新机制

这里的“好友对话”主要指最近会话列表中的单聊会话，以及好友资料变更后对会话摘要、头像、未读数、置顶/免打扰/草稿等 UI 状态的影响。

### 共同依赖的前端输入

两套前端都依赖：

- `POST conversation/sync`：同步最近会话。
- `POST conversation/extra/sync`：同步草稿、置顶、免打扰、浏览位置等扩展。
- `POST conversations/{channelId}/{channelType}/extra`：更新会话扩展。
- `DELETE conversations/{channelId}/{channelType}`：删除最近会话。
- `GET channels/{channelId}/{channelType}`：获取单聊或群聊频道资料。
- WebSocket CMD：`channelUpdate`、`unreadClear`、`conversationDeleted`、`onlineStatus` 等。

### `sections/im_web` 的实现

`im_web` 最近会话由 `packages/datasource-vue/src/stores/conversationStore.ts` 持有，频道资料由 `channelStore.ts` 缓存，列表 UI 在 `ConversationList.vue`。

首屏加载：

- `MainLayout.vue` 在用户已登录时先 `groupStore.fetchMyGroups()`，再 `conversationStore.ensureGroupConversations()` 和 `conversationStore.syncConversations()`。
- `ConversationList.vue` 挂载后调用 `loadConversationList`，顺序执行 `syncGroupConversations` 与 `syncConversations`；失败时最多重试 5 次，延迟从 3 秒递增到 15 秒。

`conversationStore.syncConversations` 的处理逻辑：

1. 调 `syncApi.syncConversations({ msg_count: 1 })`。
2. 如果响应中带 `users` 或 `groups`，先预热 `channelStore`，避免列表逐项渲染时再拉频道详情。
3. 对每个 conversation 做标准化，字段统一为 `channel_id`、`channel_type`、`unread`、`last_msg_seq`、`last_msg_time`、`last_message`、`top`、`mute`、`draft`。
4. 对被用户手动删除或隐藏的会话做本地抑制：只有当后端出现更新的 `last_msg_seq` 或时间戳时才重新显示。
5. 调 `syncExtra` 合并草稿、置顶、免打扰等扩展。
6. 调 `ensureGroupConversations`，把“我保存的群聊”补成会话项，避免后端最近会话为空时群聊入口消失。
7. 对缺少摘要的群聊，通过 `message/channel/sync` 预取最近消息生成摘要。

实时更新：

- 收到普通消息时，`messageStore.addMessage` 会调用 `conversationStore.addOrUpdateConversation`，更新摘要、时间、未读数。
- 当前会话正在打开时，`ChatView.vue` 和全局 message listener 会调用 `conversationStore.clearUnread`。
- `unreadClear` CMD 直接把 `unreadMap` 和会话对象 unread 置零。
- `conversationDeleted` CMD 调本地删除。
- `channelUpdate` CMD 清理频道缓存后重新拉取频道资料。

好友单聊的一个关键细节是频道归属修正：当 SDK 消息的单聊 `channelID` 是当前用户自己、`fromUID` 是对方时，`resolveVisibleMessageChannel` 会把可见频道改为对方 UID。这样消息不会落到“自己和自己”的会话，而是正确更新好友单聊。

会话 UI：

- `ConversationList.vue` 读取 `conversationStore.sortedConversations`。
- 摘要展示通过 `buildDigestPresentation` 做消息类型兜底，例如图片、语音、文件、系统消息。
- 右键菜单支持删除、隐藏、置顶、免打扰等操作。
- 删除会话会先本地移除，再调用后端；如果远端删除失败会回滚。
- 草稿既有远端同步，也有 local-only 会话草稿存储，按当前登录用户作用域隔离。

### `TangSengDaoDaoWeb` 的实现

TangSengDaoDaoWeb 的最近会话列表由 `packages/tsdaodaobase/src/Pages/Chat/vm.ts` 的 `ChatVM` 控制，数据主要来自 SDK `conversationManager`。

首屏加载：

- `ChatVM.didMount` 检查 `WKSDK.shared().connectManager.status`。
- 如果已连接，调用 `reloadRequestConversationList()`。
- `reloadRequestConversationList` 调 `WKSDK.shared().conversationManager.sync({})`，这个 sync 会触发 `DataSourceModule.setSyncConversationsCallback`，最终请求 `conversation/sync`。
- 返回的会话被转成 SDK `Conversation`，再包装为 `ConversationWrap`。

实时更新：

- `ChatVM` 监听 `conversationManager.addConversationListener`。
- `ConversationAction.add`：新会话插入列表头部。
- `ConversationAction.update`：找到已有会话后更新引用，过滤敏感词，重新排序。
- `ConversationAction.remove`：从列表移除。
- `channelManager.addListener` 用于频道资料变化，例如置顶状态变化后重新排序。
- 消息删除监听会在删除的是最近一条消息时把 lastMessage 回退到上一条。

排序策略：

- `ChatVM.sortConversations` 以最近消息时间排序。
- 置顶会话通过给排序分数增加一个很大的偏移量置顶。

扩展属性：

- `ChannelDataSource.conversationExtraUpdate` 调 `conversations/{channelID}/{channelType}/extra`，上报 `browse_to`、`keep_message_seq`、`keep_offset_y`、`draft`。
- SDK 的 `syncConversationExtrasCallback` 再通过 `conversation/extra/sync` 拉取扩展并转成 `ConversationExtra`。

菜单和未读：

- `apps/web/src/App/index.tsx` 注册“会话”菜单时遍历 `WKSDK.shared().conversationManager.conversations` 汇总 unread。
- Electron 环境下会把 unread 同步给桌面进程。

### 对比结论

| 对比点 | `sections/im_web` | `TangSengDaoDaoWeb` |
| --- | --- | --- |
| 最近会话来源 | `conversationStore` 主动请求并规范化 REST 响应 | `conversationManager.sync` 触发 provider，请求后转 SDK Conversation |
| 好友资料缓存 | `channelStore` 普通对象缓存 | `channelManager` SDK 缓存 |
| 单聊归属修正 | 显式处理 `channelID` 与 `fromUID` 的可见频道 | 依赖 SDK `Channel` 等价判断和 conversationManager |
| 删除/隐藏 | 有本地 suppress 记录，避免刷新后旧会话立即复活 | 直接通过 SDK conversation remove 和后端删除 |
| 草稿/置顶/免打扰 | Pinia + localStorage + `conversation/extra` | SDK `ConversationExtra` + provider callback |
| UI 更新方式 | Vue 响应式 store 驱动 | VM notifyListener + SDK manager listener |

`im_web` 的好友对话更新更强调可恢复、可回滚和本地用户操作保护；TangSengDaoDaoWeb 则让 SDK 的会话管理器承担更多状态聚合责任。

## 好友添加机制

### 共同依赖的前端输入

两套前端都使用这些后端能力：

- `GET friend/sync`：同步好友列表。
- `GET user/search`：搜索用户。
- `POST friend/apply`：发送好友申请。
- `GET friend/apply`：获取好友申请列表。
- `POST friend/sure`：同意好友申请。
- `DELETE friend/apply/{toUid}`：删除申请记录。
- `GET user/reddot/friendApply` 与 `DELETE user/reddot/friendApply`：好友申请红点。
- WebSocket CMD：`friendRequest`、`friendAccept`、`friendDeleted`。

### `sections/im_web` 的实现

联系人状态由 `packages/contacts-vue/src/stores/contactStore.ts` 持有。

好友列表同步：

- `syncContacts` 调 `friendApi.syncFriends({ version, limit: 1000, api_version: 1 })`。
- 返回直接数组或 `friends` 字段都能兼容。
- 仅保留 `is_deleted !== 1` 且 `follow === 1` 的好友。
- 使用最后一项的 `version` 作为下次增量同步游标。
- 使用 request id 防止旧请求覆盖新请求。
- `groupedContacts` 通过拼音首字母分组，供联系人列表展示。

添加好友：

- `AddFriendPage.vue` 搜索前先 `contactStore.syncContacts()`，保证“已是好友/自己/可申请”的判断基于最新列表。
- `friendApi.searchUser(keyword)` 返回存在用户后，`getFriendSearchState` 判断：
  - 搜索到自己：提示不能添加自己。
  - 已是好友：提供进入会话入口。
  - 可申请：展示验证消息输入框。
- `friendApi.applyFriend({ to_uid, remark, vercode })` 发送申请。
- 对 TangSengDaoDao 后端中“申请已发出但 CMD 通知可能报错”的情况，页面会把部分非关键错误视为发送成功，避免用户重复提交。

新的朋友：

- `FriendRequestsPage.vue` 挂载后调用 `contactStore.fetchFriendRequests()`。
- 随后 `markFriendRequestsRead()` 把本地 unread 置零并调用 `user/reddot/friendApply` 删除红点。
- 同意申请调用 `friendApi.approveFriend(token)`。
- 成功后本地把该申请状态置为 accepted，并并发 `syncContacts` 与 `fetchFriendRequests`。
- 如果同意接口出现 CMD 发送类非阻塞错误，前端仍显示“已同意”，再用 `Promise.allSettled` 触发补同步。

实时 CMD：

- `registerCMDListeners` 收到 `friendRequest`、`friendAccept`、`friendDeleted` 后派发浏览器事件。
- `contactStore` 初始化时监听这些事件：
  - `friendRequest`：重拉申请列表并刷新红点。
  - `friendAccept`：重拉联系人和申请列表。
  - `friendDeleted`：重拉联系人。
- 登出时监听 `tsdaodao:logout` 清空联系人、申请和黑名单状态。

黑名单：

- `fetchBlacklist` 调 `user/blacklists`。
- `UserProfileDrawer` 中删除好友、拉黑后会触发 `contactStore.syncContacts()` 以更新联系人列表。

### `TangSengDaoDaoWeb` 的实现

TangSengDaoDaoWeb 的好友添加分散在 `DataSource`、`BaseModule` 和联系人模块 VM 中。

好友列表同步：

- `WKApp.startMain()` 登录后调用 `WKApp.dataSource.contactsSync()`。
- `DataSource.contactsSync` 从当前 `contactsList` 取最大 version。
- `CommonDataSource.contactsSync(version)` 调 `friend/sync`，将返回值转成 `Contacts` 对象。
- 新旧列表按 UID 合并，再通过 `notifyContactsChange` 通知联系人 UI。

添加好友：

- `FriendAdd` 页面通过 `WKApp.dataSource.commonDataSource.searchUser(keyword)` 调 `user/search`。
- 搜索成功后打开 `UserInfo` 页面。
- `UserInfo` 中实际发送申请，调用 `CommonDataSource.friendApply({ uid, remark, vercode })`，底层是 `POST friend/apply`。

新的朋友：

- `NewFriendVM.didMount` 先调用 `WKApp.shared.friendApplyMarkAllReaded()` 清红点。
- `getFriendApply` 调 `/friend/apply` 拉申请列表。
- `friendSure` 调 `WKApp.dataSource.commonDataSource.friendSure(token)`，同意后删除申请记录并重拉列表。
- `NewFriendVM` 自己也监听 `chatManager.addCMDListener`，收到 `friendRequest` 时重拉申请列表。

全局 CMD：

- `BaseModule` 收到 `friendRequest` 时构造 `FriendApply` 对象，写入 `WKApp.shared` 的本地申请缓存，刷新红点并播放提示音。
- 收到 `friendAccept` 时调用 `WKApp.dataSource.contactsSync()`，并把本地对应申请标成 accepted。
- 收到 `friendDeleted` 时调用 `contactsSync()`。

红点：

- `WKApp.shared.setFriendApplysUnreadCount` 调 `/user/reddot/friendApply`，把数量写入 localStorage，并刷新菜单。
- `apps/web/src/App/index.tsx` 注册通讯录菜单时读取 `WKApp.shared.getFriendApplysUnreadCount()` 作为 badge。

### 对比结论

| 对比点 | `sections/im_web` | `TangSengDaoDaoWeb` |
| --- | --- | --- |
| 联系人状态 | Pinia `contactStore.contacts` | `WKApp.dataSource.contactsList` |
| 好友申请状态 | Pinia `friendRequests` + 后端红点 | `WKApp.shared` 本地 FriendApply 缓存 + 后端红点 |
| CMD 分发 | 全局 CMD listener 转浏览器事件，store 统一处理 | BaseModule 和页面 VM 都可能监听 CMD |
| 搜索后状态判断 | 前端显式判断自己/已好友/可申请 | 搜索成功后打开用户资料页，资料页决定操作 |
| 同意好友容错 | 对 CMD 非阻塞失败做成功兜底并补同步 | 主要依赖接口成功和 contactsSync |
| 数据分组 | Pinia computed 拼音分组 | 由联系人组件和 DataSource 列表驱动 |

`im_web` 更像现代 SPA 的集中式状态流；TangSengDaoDaoWeb 保留了原 PC 客户端的模块化事件体系，好友申请既能被全局菜单感知，也能被具体页面 VM 感知。

## 群聊功能机制

### 共同依赖的前端输入

群聊功能涉及的后端能力包括以下几类。两套前端都覆盖建群、群列表、成员读取、加人、移人、群设置、二维码等主体能力；`im_web` 额外在前端暴露了邀请审批、禁言、解散、黑名单和 Clowder 成员等更完整的管理入口。

- `POST group/create`：创建群。
- `GET group/my`：获取我保存的群聊。
- `GET groups/{groupNo}`：获取群详情。
- `GET groups/{groupNo}/membersync` 和 `GET groups/{groupNo}/members`：同步或分页获取群成员。
- `POST groups/{groupNo}/members`：添加成员。
- `POST groups/{groupNo}/member/invite`：需要审批的邀请。
- `DELETE groups/{groupNo}/members`：移除成员。
- `PUT groups/{groupNo}/members/{uid}`：修改成员属性。
- `PUT groups/{groupNo}/setting`：修改群设置。
- `POST groups/{groupNo}/managers`、`DELETE groups/{groupNo}/managers`：任免管理员。
- `POST groups/{groupNo}/transfer/{uid}`：转让群主。
- `GET groups/{groupNo}/qrcode`、`GET groups/{groupNo}/scanjoin`：二维码与扫码入群。
- `POST groups/{groupNo}/exit`、`DELETE groups/{groupNo}/disband`：退群、解散。
- `POST groups/{groupNo}/forbidden/{on}`、`POST groups/{groupNo}/forbidden_with_member`：禁言。
- 群相关 CMD：成员变化、管理员变化、群主转让、黑名单、禁言、头像更新等。

### `sections/im_web` 的实现

群状态由 `packages/datasource-vue/src/stores/groupStore.ts` 管理，频道详情由 `channelStore` 辅助，群设置 UI 在 `GroupSettingsDrawer.vue` 和 `GroupMemberList.vue`。

群列表和会话入口：

- `groupStore.fetchMyGroups` 调 `group/my`，把结果 normalize 后写入 `groups` 字典。
- `conversationStore.syncGroupConversations` 会先拉我的群，再调用 `ensureGroupConversations` 把群补进会话列表。
- 对没有最近消息摘要的群，`prefetchMissingGroupConversationSummaries` 会拉 `message/channel/sync` 生成摘要。

创建群：

- `CreateGroupPage.vue` 挂载后同步联系人，并加载 Clowder 猫猫联系人目录。
- 选择成员时区分真人 UID 和 Clowder cat contact id。
- 调 `groupApi.createGroup({ name, members: selectedHumanUids })` 创建真实 IM 群，后端只接收真人成员。
- 如果选择了猫猫成员，再调用 `clowderStore.syncMixedGroupCats` 维护前端/Clowder 侧的猫猫成员信息。
- 创建后 `groupStore.upsertGroup`，必要时更新邀请确认设置，最后跳转到 `/chat/conversation/{groupNo}/2`。

群设置：

- `GroupSettingsDrawer.vue` 打开时调用 `groupStore.getGroupInfo`、`groupStore.fetchGroupMembers`、`clowderStore.loadGroupCats`。
- 群名、公告调用 `groupStore.updateGroupProfile`。
- 群头像通过 `groupApi.uploadAvatar` 上传。
- 置顶、免打扰通过 `conversationStore.togglePin`、`toggleMute` 更新会话扩展。
- 邀请确认通过 `groupStore.updateGroupSetting({ invite })`。
- 全员禁言通过 `groupStore.muteAll`。
- 群二维码通过 `groupStore.getGroupQRCode` 获取 payload，前端用 `qrcode` 库生成图片；如果群开启邀请确认，则显示审批状态而不是二维码。
- 邀请成员时前端可搜索用户，也允许逗号输入 UID；根据邀请确认开关决定调用直接邀请或审批邀请。
- 退出群、解散群使用 `AppDialog` 做二次确认，成功后删除本地会话。

群成员管理：

- `GroupMemberList.vue` 加载群详情、群成员、猫猫目录和群内猫猫成员。
- 通过当前用户 UID、群 owner/creator、成员 role 判断是否可管理。
- 支持移出成员、任免管理员、成员禁言、转让群主、加入群黑名单。
- 对猫猫成员，走 `clowderStore.addGroupCat/removeGroupCat`，不调用 IM 群成员接口。

实时更新：

- `registerCMDListeners` 收到 `memberUpdate` 或 `groupMemberAdd`、`groupMemberRemove`、`groupManagerUpdate`、`groupTransferOwner`、`groupBlacklistUpdate`、`groupForbiddenUpdate` 等 CMD 时，会清理群缓存，重新拉 `getGroupInfo`、`fetchGroupMembers`，并调用 `conversationStore.ensureGroupConversations()`。
- `groupAvatarUpdate` 会清理频道和群缓存并重新拉取。

### `TangSengDaoDaoWeb` 的实现

TangSengDaoDaoWeb 的群能力主要通过 `ChannelDataSource`、SDK `channelManager` 和频道设置端点组合实现。

数据源：

- `ChannelDataSource.createChannel(uids)` 调 `group/create`。
- `groupSaveList` 调 `group/my` 并把结果转为 SDK `ChannelInfo`。
- `subscribers(channel, req)` 调 `groups/{groupNo}/members` 并转为 SDK `Subscriber`。
- `addSubscribers`、`removeSubscribers`、`updateSetting`、`managerAdd`、`managerRemove`、`channelTransferOwner`、`exitChannel` 分别封装对应群接口。
- `DataSourceModule.setSyncSubscribersCallback` 调 `groups/{groupNo}/membersync`，并按 owner/manager/member 角色排序后返回给 SDK。

创建群和加人：

- `GroupSave` 页面点击“新建群”，打开 `ContactsSelect`，选中联系人后调用 `WKApp.dataSource.channelDataSource.createChannel(selectedUids)`。
- `OrganizationalGroupNew` 支持从好友或组织架构树选择成员。创建群时调用 `createChannel([...selectedUids])`，添加成员时调用 `addSubscribers(channel, selectedUids)`。
- 在单聊详情里加人时，会把当前用户、当前单聊对方和选中的联系人合成 UID 数组后调用 `createChannel`，创建新的群聊。
- 在群聊详情里加人则直接调用 `addSubscribers`。

群设置和成员：

- `ChannelSettingVM` 打开时调用 `channelManager.fetchChannelInfo(channel)` 和 `reloadSubscribers()`。
- `reloadSubscribers` 优先从 `WKSDK.shared().channelManager.getSubscribes(channel)` 读 SDK 订阅者缓存。
- SDK 订阅者变化时通过 `SubscriberChangeListener` 触发 UI 刷新。
- 频道设置、成员列表、添加成员、移除成员、退出群等功能通过 `WKApp.endpoints.registerChannelSetting` 注册到设置页中。
- 管理权限由当前用户在群内的 `Subscriber.role` 判断。

实时更新：

- `BaseModule` 收到 `memberUpdate` 时调用 `channelManager.syncSubscribes(channel)`。
- 收到频道或头像更新 CMD 时调用 `channelManager.fetchChannelInfo` 并刷新头像缓存。
- 频道资料变化通过 `channelManager.addListener` 推给相关页面 VM。

### 对比结论

| 对比点 | `sections/im_web` | `TangSengDaoDaoWeb` |
| --- | --- | --- |
| 群状态中心 | Pinia `groupStore.groups/groupMembers` | SDK `channelManager` + `ChannelDataSource` |
| 群会话补齐 | `ensureGroupConversations` 主动把保存群加入会话列表 | 保存群在联系人/群列表中展示，会话列表主要依赖 conversationManager |
| 创建群 UI | 独立 Vue 页面，支持真人 + Clowder 猫猫混合选择 | ContactsSelect/OrganizationalGroupNew，支持好友与组织架构选择 |
| 成员同步 | REST 拉取后 normalize 到 store | SDK provider 同步 Subscriber，页面从 SDK 缓存取 |
| 群设置 | Drawer + 单独成员页，操作后更新 store | 频道设置端点注册，VM + route stack 组织 UI |
| 权限判断 | 基于 groupInfo owner/creator 与当前成员 role | 基于 SDK Subscriber.role |
| 扩展成员 | 支持 Clowder cat 成员，前端单独同步 | 原生 IM 群成员，未包含 Clowder 成员概念 |

`im_web` 对群聊做了更多面向新 UI 和 AI 成员的前端扩展；TangSengDaoDaoWeb 的群聊机制则更原生、更贴近 SDK 的频道/订阅者模型，也保留了 PC 客户端的组织架构加人能力。

## 登录机制

### 共同依赖的前端输入

两套前端都依赖：

- `POST user/login`：账号密码登录。
- `GET user/loginuuid`：获取扫码登录 UUID/二维码。
- `GET user/loginstatus?uuid=...`：轮询扫码状态。
- `POST user/login_authcode/{authCode}`：扫码授权码登录。
- `POST user/register`、`POST user/sms/registercode`：注册与验证码。
- `GET users/{uid}/im`：获取 IM WebSocket 地址。
- `GET user/devices`、`DELETE user/devices/{deviceId}`、`POST user/quit`：设备管理和退出。
- HTTP token header：所有需要鉴权的 REST 请求都由前端在请求拦截器中注入 token。

### `sections/im_web` 的实现

登录相关代码在 `packages/login-vue/src/stores/loginStore.ts`、`packages/login-vue/src/views/LoginPage.vue`、`packages/login-vue/src/views/RegisterPage.vue` 和 `packages/datasource-vue/src/stores/userStore.ts`。

账号密码登录：

- `LoginPage.vue` 收集手机号/用户名和密码。
- `loginStore.normalizeUsername` 会把 11 位手机号转换成 `0086` 前缀形式。
- `buildLoginDevice` 生成稳定 `device_id`，并限制 `device_id`、`device_name`、`device_model` 长度，避免后端字段超长。
- `loginStore.loginWithPassword` 调 `userStore.login`，后者请求 `authApi.login`。
- 登录成功后 `userStore.applyLoginResult` 保存 token、uid、name、loginInfo，并初始化 SDK。

扫码登录：

- `startQrLogin` 调 `authApi.getLoginUUID()` 获取 UUID。
- `pollQrLoginStatus` 调 `authApi.getLoginStatus(uuid)`，并把后端状态规范化为 `qr_waiting`、`qr_scanned`、`qr_confirmed`、`qr_expired`、`qr_rejected`、`qr_failed`。
- 确认后 `confirmQrLogin` 调 `authApi.loginWithAuthCode(authCode)`，再复用 `userStore.applyLoginResult`。
- 当前 UI 是以 UUID 占位方式展示扫码状态，不像原版那样直接渲染后端返回二维码图片。

注册：

- `RegisterPage.vue` 调 `authApi.getRegisterSmsCode` 获取验证码。
- 调 `authApi.register` 注册后，立即调用 `loginStore.loginWithPassword` 登录。

登录态存储：

- `StorageService` 按 URL 查询参数 `sid` 做 key 后缀，支持多 session 隔离。
- 保存项包括 `token`、`uid`、`name`、`loginInfo`。
- `userStore` 初始化时如果读到 token 和 loginInfo，会恢复 currentUser，并立即初始化 SDK。

SDK 连接：

- `useSdkStore.initializeSDK` 通过 `apiClient.get(users/{uid}/im)` 获取连接地址。
- `resolveWebsocketConnectAddr` 负责地址规范化和远程浏览器 host 重写。
- 连接状态以 `connectionState` 暴露为 `connected`、`connecting`、`reconnecting`、`offline`、`kicked`。
- 断线时指数退避重连，最大延迟 30 秒。
- 连接成功后执行恢复同步。
- 被踢或鉴权失败时进入 `kicked` 状态，`MainLayout.vue` 展示 banner，`KickoutOverlay` 引导重新登录。

退出：

- `userStore.logout` 默认调用 `authApi.quit()`。
- 清除 scoped storage 和用户态。
- 重置 channel/group/conversation/message stores。
- 派发 `tsdaodao:logout` 让联系人 store 清理。
- 调 `sdkStore.disconnect()` 断开 SDK。

路由守卫：

- `router.beforeEach` 检查 `StorageService.get('token')`。
- 访问 `/chat` 下需要登录的路由时，没有 token 会跳转 `/login`。

### `TangSengDaoDaoWeb` 的实现

登录相关代码在 `packages/tsdaodaologin/src/login_vm.tsx`、`packages/tsdaodaologin/src/login.tsx`、`packages/tsdaodaobase/src/App.tsx` 和 `apps/web/src/index.tsx`。

应用启动：

- `apps/web/src/index.tsx` 根据运行环境设置 API 地址：
  - Tauri/Electron 或开发环境使用固定远端地址。
  - Web 生产环境使用 `/api/v1/`。
- 设置 `WKApp.apiClient.config.tokenCallback`，所有请求从 `WKApp.loginInfo.token` 读取 token。
- 调 `WKApp.loginInfo.load()` 从 localStorage 恢复登录态。
- 注册 `BaseModule`、`DataSourceModule`、`LoginModule`、`ContactsModule`。
- 调 `WKApp.shared.startup()`。

账号密码登录：

- `LoginVM.requestLoginWithUsernameAndPwd` 调 `user/login`。
- 前端会把手机号补成 `0086` 或 `00` 开头形式。
- 请求参数包含 `flag` 和 `device`，设备信息来自 `WKApp.shared.deviceId/deviceName/deviceModel`。
- 登录成功后 `loginSuccess` 写入 `WKApp.loginInfo` 并 `save()`。
- 然后调用 `WKApp.endpoints.callOnLogin()`，触发 `WKApp.startMain()`。

扫码登录：

- `LoginVM` 是一个状态机，状态包含 `getUUID`、`waitScan`、`scanned`、`authed`、`expired`。
- `requestUUID` 调 `user/loginuuid`，参数带设备信息，返回 `uuid` 和 `qrcode`。
- UI 用 `qrcode.react` 渲染二维码。
- `pullLoginStatus` 轮询 `user/loginstatus?uuid=...`。
- 扫码成功后用 `user/login_authcode/{authCode}` 换 token。
- 二维码过期后自动刷新，超过最大次数后要求用户手动刷新。

登录态存储：

- `LoginInfo.save` 把 `app_id`、`short_no`、`uid`、`token`、`name`、`role`、`is_work`、`sex` 按 `sid` 后缀写入 localStorage。
- `LoginInfo.isLogined()` 只检查 token 是否存在。
- `logout()` 清 token 等字段后刷新页面。

SDK 连接：

- `WKApp.startup` 设置设备信息、主题、通知偏好和远端配置。
- `connectAddrCallback` 调 `WKApp.dataSource.commonDataSource.imConnectAddrs()`，底层请求 `users/{uid}/im`，优先取 `wss_addr`，否则用 `ws_addr`。
- 已登录时直接 `startMain()`。
- `startMain` 调 `connectIM()`，同步联系人，加载敏感词配置，并获取当前设备 ID 写入 `WKSDK.shared().config.clientMsgDeviceId`。
- `connectIM` 设置 `WKSDK.shared().config.uid/token` 并调用 `connect()`。
- 连接被踢或鉴权失败时调用 `WKApp.shared.logout()` 刷新回登录态。
- 断线时如果有多个连接地址，会轮转地址重试。

### 对比结论

| 对比点 | `sections/im_web` | `TangSengDaoDaoWeb` |
| --- | --- | --- |
| 登录态中心 | `userStore` + scoped `StorageService` | `WKApp.loginInfo` 全局单例 |
| 登录成功后动作 | 保存 token，初始化 SDK，Pinia 响应式更新 | 保存 loginInfo，触发 onLogin endpoint，`WKApp.startMain` |
| 扫码登录 UI | 状态化占位展示 UUID/状态 | 后端 qrcode + `qrcode.react` 真实二维码 |
| SDK 地址 | `users/{uid}/im` + 地址规范化/host 重写 | `imConnectAddrs` 优先 `wss_addr`，支持地址轮转 |
| 重连/踢出 | Pinia 暴露状态，UI banner/overlay 呈现 | SDK listener 中 logout 并刷新页面 |
| 退出 | 调 `user/quit`，清 store，断 SDK | 清 loginInfo 并 reload |
| 多 session | `sid` 后缀存储 token/loginInfo | `LoginInfo` 也按 `sid` 后缀存储字段 |

`im_web` 的登录机制更偏 SPA 状态管理，强调可视化连接状态、重连恢复和 store 清理；TangSengDaoDaoWeb 更偏传统 PC 客户端启动流程，通过全局 `WKApp` 串联模块、SDK、菜单和桌面环境。

## 前端实现总结

从纯前端角度看，两套项目依赖同一个 `sections/im` 后端和同一个 WuKongIM SDK，但架构取向不同：

- `sections/im_web` 把后端响应和 SDK 事件全部折叠为 Pinia store 中的普通前端状态。优点是状态可测试、可组合、可针对 AI/Clowder 做扩展和容错；代价是前端需要自己承担更多去重、补拉、恢复和字段兼容逻辑。
- `TangSengDaoDaoWeb` 把 SDK manager 作为核心状态容器，前端通过 provider callback 把后端接口接入 SDK，再由 React VM 监听 SDK 对象变化。优点是贴近原生 IM 客户端模型，PC/Web/Electron 扩展成熟；代价是状态分散在 `WKApp`、SDK manager、页面 VM 和本地缓存之间，追踪具体状态来源时需要沿模块注册链路查找。

如果后续继续完善 `im_web`，可以优先保持当前方向：REST API adapter 只做后端接口封装，Pinia store 持有前端状态，SDK listener 只负责事件入口，UI 组件只消费 store。这样在引入更多 AI 消息、混合群成员、流式回复和恢复场景时，会比直接复制 TangSengDaoDaoWeb 的全局 `WKApp` 体系更容易隔离复杂度。
